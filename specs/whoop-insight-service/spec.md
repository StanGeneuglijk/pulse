# Spec: whoop-insight-service

**Status:** built
**Depends on:** whoop-service (synced data, `read_token`), whoop-nutrition-service (optional: meals, goal), an LLM provider

## Summary

Give a connected user a short, plain-language insight about their recent recovery, sleep and training — and, when they log meals, how their eating relates to it — generated by an LLM on demand for a day, a week or a month. Keep the cost of doing that bounded and predictable per user and for the platform.

## User stories

### US1 — Get an insight about my recent data (P1)

As a connected user, I want to ask for an insight over the last day, week or month, so that I understand what my numbers mean and what to do next.

**Independent test:** with synced data in the database and a fake LLM, request a weekly insight; one is stored and returned.

**Acceptance scenarios**

1. **Given** I have WHOOP data in the window, **when** I request a weekly insight, **then** I receive a 3–5 sentence insight ending with one actionable suggestion.
2. **Given** I have no WHOOP data in the window, **when** I request one, **then** I get `422` and no LLM call is made.
3. **Given** the period is `daily`, `weekly` or `monthly`, **when** I request it, **then** the window length, reasoning effort and answer length follow that period — I can't choose them directly.
4. **Given** the LLM provider fails, **when** I request an insight, **then** I get `502` with a generic message and the failure is recorded.

### US2 — Nutrition makes it better, but isn't required (P2)

As a user who logs meals, I want the insight to take what I ate and my goal into account, so that it can connect eating to recovery.

**Acceptance scenarios**

1. **Given** I logged meals and set a goal, **when** I request an insight, **then** the prompt includes my meals and goal and the insight may reference them.
2. **Given** I never logged a meal, **when** I request an insight, **then** the prompt is WHOOP-only — no empty nutrition section.

### US3 — Never pay twice, never overspend (P1)

As the operator, I want spending bounded per user and in total, and duplicates avoided, so that cost is predictable.

**Acceptance scenarios**

1. **Given** a generation for me is in progress, **when** I request another, **then** I get `409` and no second LLM call is made.
2. **Given** my inputs haven't changed since my last insight for this period, **when** I request it again, **then** the stored insight is unchanged.
3. **Given** my estimated spend reached the per-user cap, **when** I request an insight, **then** I get `402` before any LLM call; other users are unaffected.
4. **Given** total estimated spend reached the platform cap, **when** anyone requests an insight, **then** they get `402`.
5. **Given** a model that isn't in the price table is configured, **when** the service starts, **then** it refuses to start.

### US4 — See my history and usage (P3)

As a user, I want to list my past insights, fetch the latest per period, and see my usage.

**Acceptance scenarios**

1. **Given** I generated insights, **when** I list them, **then** I see mine, newest first, optionally filtered by period.
2. **Given** someone else's user id, **when** I request their insights with my credential, **then** I get `401`.

## Functional requirements

- **FR-001** Read WHOOP data (and nutrition data when present) from the shared database, read-only; never migrate tables this service doesn't own.
- **FR-002** Build the prompt from the data window; omit optional sections that are empty.
- **FR-003** Call the LLM through a provider-agnostic interface with an explicit output ceiling and effort level set per period.
- **FR-004** Check the per-user cap, then the platform cap, then a per-user lock — all before the LLM call.
- **FR-005** Store insights idempotently, keyed on user, period, window and prompt version.
- **FR-006** Record every attempt with its token usage; estimate spend from usage × a price table.
- **FR-007** Per-user routes accept the operator key or that user's `read_token` (issued by whoop-service).
- **FR-008** Restrict the configurable model to models the price table covers.

## Key entities

- **Insight** — the generated text for one user, period and window, with the prompt version and model that produced it.
- **Insight job log** — one generation attempt: status, token usage, duration, error.
- **Activity log** — one API hit.

## Success criteria

- **SC-001** No request can make the platform spend more than one call past a cap.
- **SC-002** A double-click never produces two paid calls.
- **SC-003** An empty data window is never billed.
- **SC-004** The full test suite runs without network access or spend.

## Out of scope

- Scheduled or push insights — on demand only; a queue and worker come if generations become long or scheduled.
- Medical advice or diagnosis — the prompt forbids medical claims.
- Chat or follow-up questions about an insight.
- Owning or syncing any WHOOP data.
